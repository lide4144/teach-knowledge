# 复习题 2026-08-16

## Q1: 为什么 Speculative Decoding 是纯加速而不是近似？

Speculative Decoding 让 draft model 先猜 k 个 token、再由 target model 验证。请解释：

1. 为什么它能保证最终输出分布与不用投机解码时**完全一致**，而不是一种有损近似？
2. 既然每轮都要 draft + verify 两步，为什么整体反而更快？请结合推理瓶颈（compute vs memory bandwidth）说明。
3. 由此推论：为什么「接受率 < 50% 的投机解码是负优化」？

<details><summary>参考答案</summary>

1. **输出一致的原因**：接受/拒绝机制是逐位比对的——被接受的 token 必须同时得到 target model 的认可；第一个被 target model 拒绝的位置，直接用 target model 自己采样的结果替换，之后的草稿全部丢弃。所以每个最终写出的 token 要么经过 target model 验证，要么直接由 target model 产生，输出分布与单独跑 target model 完全一致。

2. **更快的原因**：自回归生成的瓶颈在 memory bandwidth（每生成 1 个 token 都要把全部权重从显存读一遍），而不是 compute。串行生成 k 个 token 需要 k 次完整前向（读 k 遍权重）；投机解码把 k 个位置合并成 target model 的**一次并行前向**（只读一遍权重，GPU 算力本来闲置，并行算 k 个位置几乎不额外耗时）。draft model 很小，起草成本远低于省下的主模型前向次数。

3. **负优化的原因**：接受率低意味着大多数草稿 token 被丢弃，但 draft 开销和 verify 的一次主模型前向已经付出去了。一轮只净产出 1-2 个 token 时，相比裸跑（一次前向稳定产出 1 个 token）只是白白多花草稿的显存和计算，净吞吐反而下降。

**评分要点**
- 答出「拒绝位置由 target model 输出替换 / 接受前缀需经 target 认可」这一机制 → 得 1/3
- 答出「瓶颈是 bandwidth 不是 compute，k 个位置一次并行前向只读一遍权重」→ 得 1/3
- 答出「低接受率 = 白付 draft + verify 成本而净产出少」→ 得 1/3

</details>

## Q2: MoE 省的是什么，不省的是什么？

同事说：「Gemma4-26B-A4B 是 MoE 模型，26B 总参数但每 token 只激活 4B，所以它在本地既跑得快又省显存。」这句话**一半对一半错**。请指出哪半对、哪半错，并从推理的硬件瓶颈角度解释原因。最后说明：在什么部署场景下 MoE 的劣势会变得尤其明显？

<details><summary>参考答案</summary>

- **对的一半：跑得快。** 推理速度的瓶颈是 memory bandwidth——每生成一个 token 都要把**激活的**权重从显存读一遍。稠密 27B 每 token 读 ~16GB，MoE 26B-A4B 每 token 只读 ~4B 激活部分（128 个专家中 router 只激活 top-8），所以速度对标 4B 稠密模型（实测 60-78 t/s vs 稠密的 5-10 t/s）。
- **错的一半：不省显存。** 显存占用按**总参数**算：虽然每 token 只用 4B，但全部 128 个专家的权重都必须驻留在显存里，26B 的 Q4 依然要 ~16.8GB。MoE 省的是 bandwidth，不是 memory capacity。
- **劣势明显的场景**：显存容量紧张的场景（如小显存消费级 GPU 想跑大模型）。MoE 让你用 4B 的速度跑 26B 的质量，但前提是你装得下 26B——一张 8-12GB 的卡装不下总参数，MoE 的速度优势根本无从谈起。此时小稠密模型或更激进的量化才是出路。

**评分要点**
- 明确区分「省 bandwidth 不省 capacity」两个概念 → 核心，得 1/2
- 用「每 token 读激活权重 vs 全部专家权重必须驻留显存」解释机制 → 得 1/4
- 举出显存受限场景说明 MoE 劣势 → 得 1/4

</details>

## Q3: 场景判断——该选哪个量化档？

你拿到两个模型的 GGUF 发布页：

- **模型 A**（Gemma4）：官方做过 QAT 到 ~4bit，只发布 `Q4_K_M` 一个量化档
- **模型 B**：普通 PTQ 模型，发布页上从 `Q2_K` 到 `Q8_0` 十几档俱全

请回答：

1. 对模型 A，有人觉得「Q4 质量不够，想要 Q6/Q8 版本」，为什么这个诉求对 QAT 模型基本没意义？
2. 对模型 B，选量化档时的权衡逻辑和模型 A 有何本质不同？
3. 总结成一条「选量化档的第一原则」。

<details><summary>参考答案</summary>

1. **QAT 模型要更高精度档没意义**：QAT 在训练过程中就模拟了 4bit 量化，模型权重已经「适应」了量化误差，4bit 就是官方对齐好的甜点。Q6/Q8 要多花 40-100% 的磁盘和带宽，质量却几乎零提升——质量损失本来就被训练消掉了，买更高精度买不到东西。反过来选 Q3/Q2 也是浪费：那会偏离 QAT 对齐好的 4bit 甜点，重新引入训练时没有适应过的误差。

2. **PTQ 模型的权衡逻辑本质不同**：PTQ 是训练完之后硬压，模型没有为适应低精度做过任何调整，精度损失随 bit 数降低而明显增大。所以选档是一个真实的 trade-off：显存/带宽预算 vs 可接受的质量损失，需要逐档试（常见折中是 Q4_K_M ~ Q6_K）。而 QAT 模型根本不存在这个权衡——官方已经替你选好了。

3. **第一原则**：先看模型是不是 QAT 原生低 bit。是的话直接拿官方甜点档，不用纠结；不是的话（纯 PTQ），才需要在质量损失和带宽/显存预算之间逐档权衡。

**评分要点**
- 答出「QAT 训练中已适应量化误差，4bit 是对齐好的甜点」→ 得 1/3
- 答出「PTQ 存在真实的质量-体积 trade-off，QAT 不存在」→ 得 1/3
- 第一原则表述为「先判断是否 QAT 原生低 bit」→ 得 1/3

</details>

## Q4: 排查实战——DFlash 在 Vulkan 上必崩

你在 llama.cpp 上给 MoE 模型配 Speculative Decoding：用 DFlash 草稿器，Vulkan 后端，首个请求就静默死掉（exit 5、无日志），换模型、换草稿精度（Q8/BF16）都复现。但你清楚记得这套配置「以前成功过」。请给出你的排查思路和最终结论，并说明：

1. 为什么「换模型、换草稿精度都复现」这条信息，足以让你把怀疑方向从「配置问题」转向「后端实现问题」？
2. 「以前成功过」的记忆最可能的解释是什么？
3. 如果换用 ROCm 后端后发现接受率只有 27%，下一步该做什么，依据是什么？

<details><summary>参考答案</summary>

1. **变量隔离逻辑**：模型换了（26B/35B 两个）、草稿精度换了（Q8/BF16 两种），问题稳定复现——这些变量都被排除了，剩下的公共因子就是 Vulkan 后端的 drafter 实现本身（且 `-fa on` 崩更快进一步指向图/后端层面）。结论：是 Vulkan 的 DFlash drafter 图实现坏了，不是配置问题。排查崩溃类问题的正确顺序是**先隔离后端**，再换草稿精度，最后才调参数。

2. **「以前成功过」的解释**：那次成功是在 ROCm 后端上。DFlash 在 ROCm 下工作正常，只在 Vulkan 下必崩——记忆没错，只是后端不同。这说明排查时「环境差异」（后端、版本、上游默认值变更）往往是「以前能跑现在不能跑」的根因。

3. **接受率 27% 的下一步**：加 `--spec-draft-p-min 0.75`。依据：上游在 MTP clean-up 提交（d14ce3da, PR #23269）中把该参数默认值从 0.75 静默改成了 0.00（issue #25908），导致草稿器永远不会因低置信度提前退出，硬猜低质量内容，接受率崩溃。ROCm 上设回 0.75 后接受率从 27% → 92%。教训：关注上游默认值变更这种 silent breaking change；`timings.draft_n_accepted/draft_n` 是投机解码健康度的核心指标。

**评分要点**
- 答出变量隔离推理：公共因子只剩后端 → 得 1/3
- 答出「以前成功是在 ROCm 上」→ 得 1/3
- 答出 `--spec-draft-p-min 0.75` 及上游默认值被静默改坏的背景 → 得 1/3

</details>
