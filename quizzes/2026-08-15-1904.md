# 复习题（Closure / Git Rebase）

## Q1：Closure 的"存活"机制

有人说："外层函数执行完后，它的局部变量就被销毁了，和普通函数调用一样。" 请解释为什么这句话在存在 closure 的情况下不成立，并说明底层发生了什么。

<details>
<summary>参考答案</summary>

**参考答案**：当内层函数捕获了外层函数的变量并逃逸出去（被返回或被外部持有）时，外层函数的局部变量不会被垃圾回收，因为 closure 仍持有对这些变量的**引用**。Closure 本质是"函数 + 其定义时的 lexical environment"的捆绑，所以即使外层函数已返回，被捕获的变量依然存活、可读可写。

**评分要点**：
- [ ] 指出变量**不会**被回收，而非含糊地说"还能用"
- [ ] 解释原因：closure 持有 reference，GC 因此不回收
- [ ] 提到 closure = function + lexical environment（捆绑）这一本质
</details>

## Q2：Lexical Scope 与经典循环陷阱

下面代码输出什么？为什么把 `var` 换成 `let` 输出就变了？请从 closure 捕获的对象和作用域规则的角度解释。

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

<details>
<summary>参考答案</summary>

**参考答案**：`var` 版本输出 **3, 3, 3**。因为 `var` 只有函数作用域，三次迭代创建的三个 closure 捕获的是**同一个**变量 `i`；回调执行时循环早已结束，`i` 已是 3。`let` 版本输出 **0, 1, 2**，因为 `let` 是块级作用域，每次迭代都会创建一个**新的绑定**（新的 lexical environment），每个 closure 各自捕获独立的 `i`。

**评分要点**：
- [ ] 说对两种输出结果
- [ ] 指出 `var` 的三个 closure **共享**同一个 `i`
- [ ] 指出 `let` 每次迭代产生新绑定，closure 各自独立捕获
- [ ] 不依赖死记，而是围绕"closure 捕获的是变量绑定而非当时的值"来解释
</details>

## Q3：为什么 rebase 过的分支必须 force push？

笔记中说 "commit 是不可变对象，rebase 并不是移动提交"。请基于这个底层抽象解释：为什么 rebase 之后普通的 `git push` 会被拒绝？以及为什么这个特性恰恰推导出了 "Never rebase public history" 这条金科玉律？

<details>
<summary>参考答案</summary>

**参考答案**：Rebase 不是移动提交，而是**逐个重新创建**内容等价但哈希不同的新提交（因为 parent 变了）。所以 rebase 后本地分支和远端分支的历史已经分叉——远端是旧哈希链，本地是新哈希链，push 不是 fast-forward，被拒绝，只能 force push 覆盖。正因为 rebase **改写了历史**，如果别人已经基于旧哈希的提交在继续工作，force push 后他们的工作就全部悬空（base 不复存在），所以公共历史绝不能 rebase。

**评分要点**：
- [ ] 说清 rebase 是"重新创建新提交"而非"移动"，哈希变化的原因是 parent 改变
- [ ] 解释 push 被拒的直接原因：本地与远端历史分叉，非 fast-forward
- [ ] 把"哈希重写"与"别人基于旧哈希的工作会悬空"连成因果链
</details>

## Q4：场景判断 —— merge 还是 rebase？

你的个人知识库在两台电脑（台式机 + 笔记本）上同步。某天你在台式机上还没推送，笔记本端的改动已经推到了远端。此时 `git pull` 会产生什么？你该怎么处理，为什么这个选择在该场景下是安全的？如果换成是公司里多人协作的 `main` 分支，同样的操作还安全吗？

<details>
<summary>参考答案</summary>

**参考答案**：普通 `git pull` 默认走 merge，会产生一个 merge commit，多端频繁同步会让历史变成反复分叉的"地铁图"。应该用 `git pull --rebase`：先把本地未推送的提交摘下，快进到远端最新，再把本地提交逐个重放到新基点之上，历史保持直线，push 必为 fast-forward。这在个人知识库场景安全，因为被 rebase 的提交**只属于自己、尚未推送给别人**（可加 `--autostash` 处理脏工作区）。在公司共享的 `main` 分支上不安全：rebase 会重写哈希，同事基于旧提交的工作会悬空，公共历史应使用 merge。

**评分要点**：
- [ ] 说出普通 pull 的后果：产生 merge commit、历史分叉
- [ ] 说出 `git pull --rebase` 的三步机制（摘下 → 快进 → 重放）
- [ ] 安全判断的依据是"提交是否只属于自己的、未推送的"，而非背口诀
- [ ] 对共享分支场景能给出相反的结论（用 merge）
</details>
