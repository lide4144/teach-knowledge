# 复习题（Closure / Git Rebase）

## Q1. 词法作用域 vs 调用位置

有人说："闭包能访问外层变量，是因为调用时 JS 引擎沿着调用栈一层层往上找变量。"这个说法哪里错了？请用**词法作用域（lexical scope）**解释闭包变量存活的真正原因。

<details>
<summary>参考答案</summary>

错在"沿调用栈往上找"：作用域链由函数**定义的位置**决定，而非调用位置（这是 lexical scoping 的核心）。即使外层函数 `counter()` 已经返回、栈帧弹出，其局部变量 `count` 也不会被垃圾回收，因为返回的内层函数仍持有对该词法环境的**引用（reference）**。闭包 = 函数 + 其定义时词法环境的捆绑，所以变量在外层返回后依然存活且可访问。

**评分要点：**
- 指出作用域链由定义位置而非调用位置决定（lexical vs dynamic scoping 的区分）
- 说明外层变量不被 GC 的原因是闭包持有引用
- 不能只说"变量被保存下来了"而不提词法作用域/引用机制
</details>

## Q2. 循环闭包陷阱

下面代码输出什么？为什么改成 `let` 就能修复？

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

<details>
<summary>参考答案</summary>

输出 `3, 3, 3`。原因：`var` 只有函数作用域，整个循环只有**一个** `i` 绑定，三个回调闭包**共享**这同一个变量；等 `setTimeout` 回调执行时循环早已结束，`i` 已变为 3。

改成 `let` 后输出 `0, 1, 2`：`let` 是块级作用域，**每次迭代都会创建一个新的绑定**，每个闭包捕获的是自己那次迭代的 `i`，互不共享。

**评分要点：**
- 答出共享单一绑定 vs 每次迭代新绑定的区别
- 明白回调执行时机晚于循环结束
- 若答出也可用 IIFE 或 `setTimeout` 第三参数传值修复，可加分
</details>

## Q3. 场景判断：merge 还是 rebase

以下两个场景分别该用 merge 还是 rebase？说明理由。

1. 你把自己的 feature 分支合入团队共享的 `main` 分支，准备发版。
2. 你在个人笔记仓库的笔记本上 `git pull`，想把本地未推送的几条提交同步到远端最新状态之上。

<details>
<summary>参考答案</summary>

1. **merge**。`main` 是公共分支，rebase 会重写提交哈希（因为 parent 变了，rebase 实际是逐个重新创建内容等价的新提交），其他基于旧哈希工作的同事的历史会全部悬空。金科玉律：*Never rebase public history.* 此时应保留合并真相，用 merge commit 记录集成交付。

2. **rebase**（`git pull --rebase`）。这些提交只属于自己、尚未推送，rebase 安全。它把本地提交摘下 → 快进到远端 → 逐个重放，历史保持一条直线，push 必然是 fast-forward，不会制造多余的 merge commit。

**评分要点：**
- 判断依据是"提交是否已公开/共享"，而非个人偏好
- 场景 2 需点明直线历史 / 无合并提交 / fast-forward push 的收益
- 能提到 rebase 改写哈希所以公共分支危险
</details>

## Q4. rebase 的"移动"假象与 force push

为什么 rebase 之后必须 force push？有同事觉得"rebase 就是把我那几个 commit 挪到最新 main 上面，内容没变，凭什么要 force push？"请用 commit 的底层模型纠正他。

<details>
<summary>参考答案</summary>

Commit 是**不可变对象**，哈希由内容 + parent 等共同决定。Rebase 不是"移动"提交，而是**逐个重新创建**内容等价但 parent 不同、因而哈希也不同的新提交，旧提交被丢弃。因此 rebase 后本地分支与远端分支已经分叉（远端还指向旧哈希链），普通 push 会被拒绝为非 fast-forward，只能 force push 用新历史覆盖远端。

同事的误区在于把"内容等价"当成"同一个 commit"——内容（tree/diff）相同 ≠ 提交相同，parent 变了哈希就变了。这也是"不要在公共分支 rebase"的根源：别人引用的旧哈希会悬空。

**评分要点：**
- 说出 commit 不可变、哈希依赖 parent
- 明确 rebase = 重新创建新提交而非移动
- 能把 force push 与"改写历史"及公共分支风险联系起来
</details>
