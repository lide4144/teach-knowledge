# 复习测验 2026-08-16 08:00

## Q1：场景判断 —— 为什么 Speculative Decoding 不损失精度？

有同事质疑：「Speculative decoding 用小模型起草、大模型验证，那最终输出不就被小模型『带偏』了吗？会不会质量下降？」请解释为什么 speculative decoding 的**输出分布与不用它时完全一致**，并说明「接受率 <50% 是负优化」这句话背后的代价模型（草稿成本和什么在交换？）。

<details><summary>参考答案</summary>

**为什么不损失精度**：verify 阶段由 target model 对草稿的 k 个位置做**一次并行前向**并逐位比对。被接受的前缀恰好是 target model 自己也会生成的 token；第一个被拒位置由 **target model 自己的采样结果替换**，之后的草稿全部丢弃。所以每个落盘的 token 都来自 target model 的分布——草稿器只影响"速度"，不影响"内容"。这是纯加速而非近似。

**负优化的代价模型**：speculative decoding 的本质是**用草稿的显存/计算换 target model 的前向次数**。每轮要付出：草稿器的一次（或多次）前向 + target model 的一次并行 verify 前向（比单 token 前向略贵）。如果接受率 <50%，大多数草稿被丢弃，等于多花了一份草稿开销却只换来不到等效的串行步数节省，净吞吐反而低于裸跑。因此 `timings.draft_n_accepted/draft_n` 是核心健康指标。

**评分要点**：
- 说出"被拒位置由 target model 自己采样替换"这一关键机制
- 明确"输出分布一致 = 纯加速不是近似"
- 代价交换方向正确：草稿开销 ↔ 主模型前向次数
- 知道接受率是衡量指标（提到 draft_n_accepted/draft_n 更佳）

</details>

## Q2：对比理解 —— MoE 与 Speculative Decoding 都在"提速"，有何本质不同？

MoE（如 26B-A4B）和 speculative decoding 都能显著提升本地推理速度。请从**瓶颈、省的是什么、代价是什么**三个角度对比二者，并回答：为什么 MoE 模型"省带宽但不省显存"？

<details><summary>参考答案</summary>

**瓶颈角度**：二者都针对 decode 阶段的**内存带宽瓶颈**（每生成 1 个 token 要把激活权重从显存读一遍，算力闲置），但切入点不同。

**省的是什么**：
- MoE：通过 router 让每个 token 只激活 top-k 个 expert，**减少每步必须读取的权重量**（26B 总参数只读 ~4B 激活部分），"容量对标 26B，速度对标 4B"。
- Speculative decoding：**减少 target model 的前向次数**（一次并行 verify 产出多个 token），用算力换带宽。

**代价是什么**：
- MoE：显存按**总参数**算（26B 的 Q4 仍要 ~16.8GB），因为所有 expert 的权重都得驻留显存，随时可能被 router 选中——它省的是**每步的带宽**，不是存储。另有路由开销和负载不均衡问题。
- Speculative decoding：多一份草稿器的显存和计算，且接受率低时是负优化；batch 大、带宽不是瓶颈时收益递减。

**评分要点**：
- 指出共同前提：decode 瓶颈在带宽而非算力
- MoE 省"每步读取量" vs 投机解码省"前向次数"，区分清楚
- 答出"显存按总参数算，因为所有 expert 都必须驻留"这一因果
- 至少说出一个各自的 trade-off

</details>

## Q3：场景判断 —— QAT 模型该怎么选量化档？

你拿到两个模型：模型 A 是官方 QAT 到 ~4bit 的模型（如 Gemma4，只发布 Q4_K_M 一档）；模型 B 是普通 PTQ 模型（有 Q3 到 Q8 各种档）。同事说「量化档越高越好，给 A 找个 Q8 版本跑吧」。这个建议错在哪？如果你给一个 7B 的 PTQ 模型选档，思路和 A 有何不同？

<details><summary>参考答案</summary>

**为什么错**：QAT（Quantization-Aware Training）在**训练过程中就模拟量化**，让权重"学会"在 4bit 下保持精度，量化误差极小。A 的质量甜点已经被官方对齐在 ~4bit：
- 换 Q8：多花 40-100% 的磁盘和带宽，质量**几乎零提升**——因为信息在 QAT 训练时就已经按 4bit 表达了，更高精度只是存更多噪声。
- 换 Q3：反而破坏 QAT 对齐好的 4bit 甜点，损失比同档 PTQ 更大。

**PTQ 模型的选档思路**：PTQ 是训练完直接压，模型没"适应"过低精度，越低 bit 质量损失越明显。所以要按硬件预算在**质量-体积曲线**上自己找平衡（常见甜点是 Q4_K_M / Q5_K_M 这种 K-quant 混合精度档，关键层留高精度），而不是默认有一个官方对齐的甜点档。

**第一原则**：先看模型是不是 QAT 原生低 bit——是的话直接拿官方甜点档，不用纠结；不是的话才需要在档位间权衡。

**评分要点**：
- 答出 QAT 的核心机制：训练中模拟量化、权重对低精度鲁棒
- 解释清楚"Q8 无提升"的原因（不是"越高越好"）
- 对比出 PTQ 需要自己在质量/体积间权衡
- 提到"先判断是否 QAT 原生低 bit"这一决策顺序

</details>

## Q4：综合排查 —— 后端、参数与 git 历史

(a) 你在 llama.cpp 上启用 DFlash 投机解码，首个请求静默崩溃（无日志）。你会按什么顺序排查？为什么"先换后端"排在"调参数"之前？

(b) 你的个人笔记仓库在台式机和笔记本两端同步，`git pull` 总是产生 merge commit，历史乱成地铁图。改用 `git pull --rebase` 为什么能解决？这个操作在这里为什么是安全的，而在团队共享的 main 分支上却是危险的？

<details><summary>参考答案</summary>

**(a)** 排查顺序：**换后端 > 换草稿精度 > 调参数**。崩溃类问题（尤其静默死、无日志）通常不是配置问题而是**后端的算子/图实现坏了**——实测 DFlash 草稿器图在 Vulkan 上必崩、ROCm 上正常。如果先去调 p-min 之类参数，是在一个根本跑不起来的后端上浪费时间。先换后端能最快把问题隔离到"实现缺陷"还是"配置不当"。参数问题（如 p-min 被上游静默从 0.75 改成 0.00 导致接受率崩）表现为**能跑但接受率低**，属于另一类症状，靠 `draft_n_accepted/draft_n` 指标发现。

**(b)** `git pull --rebase` 的三步：摘下本地未推送的提交 → 快进到远端最新 → 把本地提交**逐个重放**到新基点之上。结果历史是一条直线，push 必然 fast-forward，不产生 merge commit。

**安全边界**：rebase 并不是移动提交，而是重新创建**内容等价、哈希不同**的新提交（parent 变了），即改写历史。
- 个人双端场景安全：被重写的提交**只属于自己、尚未推送给任何协作者**，没有别人的工作基于旧哈希。
- 共享 main 上危险：别人基于旧哈希的开发会全部悬空，这就是 *Never rebase public history* 的原因。

**评分要点**：
- (a) 顺序正确且能解释原因：崩溃=实现问题先隔离后端；参数问题=能跑但指标差，属另一类症状
- 提到具体证据（Vulkan 崩/ROCm 正常，或 p-min 0.75→0.00）加分
- (b) 答出"commit 不可变、rebase 是重造新哈希提交"
- 安全性的关键判据：提交是否已被他人基于（是否已推送/公开），而非"分支名字"

</details>
