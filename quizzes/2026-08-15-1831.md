# 复习测验：Closure / Git Rebase

## Q1. 理解原理（Closure）

下面这段代码中，外层函数 `counter` 已经执行完毕并返回，为什么内层函数仍然能读到并修改 `count`？请从 lexical scope 与垃圾回收的角度解释。

```javascript
function counter() {
  let count = 0;
  return function() { return ++count; };
}
const c = counter();
c(); // ?
c(); // ?
```

<details><summary>参考答案</summary>

- 内层函数是 closure，它在定义时捕获了外层函数的 lexical environment（对 `count` 的 reference），这种捕获由函数**定义的位置**决定，与调用位置无关。
- `counter()` 返回后，因为闭包仍持有对 `count` 的引用，该变量**不会被垃圾回收**，所以依然存活且可被修改。
- 输出依次是 `1`、`2`——两次调用共享并累加同一个被捕获的 `count`。

**评分要点**：
- 提到 lexical scope / 定义位置决定可访问性（而非调用位置）
- 提到闭包持有 reference，阻止了 GC
- 答对输出 1、2，并理解两次调用共享同一变量

</details>

## Q2. 场景判断（Closure 经典坑）

一位同事写了下面代码，期望依次打印 `0, 1, 2`，实际却打印 `3, 3, 3`：

```javascript
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 0);
}
```

请解释 bug 的根源，并给出修复方案。如果改用 `let`，为什么就能正常工作？

<details><summary>参考答案</summary>

- 根源：`var` 只有函数作用域，三次迭代创建的**三个 closure 共享同一个 `i` 绑定**。`setTimeout` 回调执行时循环已结束，`i` 已变成 3。
- 修复：改用 `let`。
- 原理：`let` 是块级作用域，每次迭代都会创建一个**新的绑定**，每个 closure 各自捕获当次迭代的 `i`，因此输出 `0, 1, 2`。
- （也可接受：用 IIFE 把 `i` 作为参数传入，制造每轮独立的作用域。）

**评分要点**：
- 指出「多个 closure 共享同一个变量绑定」是根源
- 说明 `let` 每次迭代产生新绑定（而不是简单说"let 是块级作用域"就完事）
- 答对修复后的输出 0, 1, 2

</details>

## Q3. 对比与权衡（Git Rebase vs Merge）

你的个人知识库在台式机和笔记本上同步。今天你在两台机器上都提交了笔记，`git pull` 时你会选 `git pull --rebase` 而不是普通 merge。请回答：

1. 普通 merge 在这种场景下会带来什么问题？
2. `git pull --rebase` 的三步过程是什么？
3. 为什么这个场景下 rebase 是**安全**的？什么情况下它会变得危险？

<details><summary>参考答案</summary>

1. 普通 merge 在远端有本地没有的提交时会产生 merge commit，多端反复同步会让历史变成不断分叉的「地铁图」。
2. 三步：① 摘下本地未推送的提交放到一边；② 快进到远端最新；③ 把本地提交逐个**重放（replay）**到新基点之上。结果是直线历史，push 必为 fast-forward。
3. 安全的原因：rebase 只改写**自己的、尚未推送**的提交。危险的情况：在共享公共分支上 rebase——rebase 并非移动提交，而是创建内容等价但哈希不同的新提交（parent 变了），别人基于旧哈希的工作会全部悬空。金科玉律：*Never rebase public history.*

**评分要点**：
- 说出 merge commit 导致历史分叉混乱
- 完整说出摘下 → 快进 → 重放三步
- 理解「commit 不可变、rebase 是重新创建新哈希提交」这一底层原因
- 明确安全边界：只 rebase 未推送的本地提交

</details>

## Q4. 综合场景判断（Closure × Rebase）

下面两个场景分别涉及上述两个概念，请判断做法是否正确并说明理由：

**场景 A**：某前端在 React 的 `useEffect` 里注册了一个定时器，发现回调里读到的 state 永远是注册那一刻的旧值。同事说「这是闭包的典型用途，没毛病」。这个说法对吗？

**场景 B**：团队成员为了「保持历史干净」，对已经 push 到共享 `main` 分支的提交执行了 rebase 并 force push。这个做法对吗？

<details><summary>参考答案</summary>

**场景 A：说法不对。** 这是 stale closure 问题，是闭包的**坑**而非「用途」——effect 的回调捕获的是渲染那一刻的变量快照。闭包本身机制没错（data privacy、callbacks 等确实是正当用途），但在这里表现为 bug，应通过补全依赖数组、用 ref 或函数式更新等方式修复。

**场景 B：做法错误。** 已推送的提交属于 public history，rebase 会创建哈希不同的新提交、改写历史，force push 后其他成员基于旧哈希的工作全部悬空。正确原则：rebase 只用于本地未推送的提交；共享分支的集成应使用 merge。

**评分要点**：
- A：识别出 stale closure，区分「闭包机制本身」与「闭包导致的坑」，能给出至少一种修复思路
- B：明确指出违反 *Never rebase public history*，并能用「哈希重写、他人工作悬空」解释后果
- 两题都要求给出**理由**，只答"对/不对"不给分

</details>
