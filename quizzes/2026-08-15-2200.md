# 复习题：Closure & Git Rebase

## Q1：Closure 的"存活"机制

有同学说："外层函数执行完，它的栈帧就销毁了，所以局部变量也就没了。" 请用 closure 的底层原理说明这句话错在哪里，并解释为什么被捕获的变量不会被垃圾回收。

<details><summary>参考答案</summary>

函数返回后，如果其局部变量仍被返回的内层函数引用（closure 捕获），这些变量就不满足垃圾回收的条件——GC 回收的是**不可达（unreachable）**的对象，而 closure 持有对这些变量的 reference，使它们依然可达。

关键点：
- Closure 是"函数 + 定义时的 lexical environment 引用"的捆绑
- 变量的可访问性由**定义位置**（lexical scoping）决定，与调用时的栈无关
- 因此变量不一定存在栈帧里；只要有闭包引用，它就存活

**评分要点**：
- 提到 closure 持有 lexical environment 的 reference（1 分）
- 提到 GC 回收的是不可达对象，被捕获变量仍可达（1 分）
- 能区分"栈帧销毁"与"变量被引用而存活"（1 分）
</details>

## Q2：场景判断 —— stale closure

一个 React 组件里，`useEffect` 中注册了 `setInterval`，回调里打印某个 state，但发现打印的永远是初始值。请用 closure 的概念解释这个 bug 的根源，并说明为什么这和 `for (var i...)` 打印出 `3, 3, 3` 的经典坑在本质上都是"闭包与环境绑定"的问题。

<details><summary>参考答案</summary>

根源：**stale closure**。effect 回调捕获的是**注册那一刻渲染**的变量快照（lexical environment），之后 state 更新触发了新的渲染、产生新的闭包，但旧的 interval 回调仍引用旧环境里的旧值。

与 `var` 循环坑的共性：两者都是闭包与"哪个环境"绑定的问题——
- `var` 坑：三个闭包共享**同一个**环境（`var` 只有函数作用域，循环中只有一个 `i` 绑定），所以都读到最终的 3；`let` 每次迭代创建新绑定，各闭包各得其所。
- stale closure：闭包绑定到了**旧的**环境快照，新值在新环境里，旧闭包看不到。

**评分要点**：
- 指出 stale closure：捕获的是渲染那一刻的变量快照（1 分）
- 说明 `var` 坑是"多个闭包共享同一绑定"（1 分）
- 归纳共性：问题都在闭包绑定到哪个 lexical environment（1 分）
</details>

## Q3：为什么 rebase 必须 force push？

小明 rebase 完分支后直接 `git push`，被远端拒绝。同事建议他 `git push --force`，他又担心"force push 很危险"。请从 commit 对象的不可变性出发，解释 rebase 到底做了什么、为什么普通 push 会失败，并给出判断"这次 force push 是否安全"的标准。

<details><summary>参考答案</summary>

Commit 是**不可变对象**，rebase 并不是"移动"提交，而是在新基点上**逐个重新创建**内容等价但哈希不同的新提交（因为 parent 变了，哈希必然变）。

普通 push 失败的原因：远端的旧提交哈希与你本地重写后的新哈希对不上，历史不再同源，push 不是 fast-forward，被拒绝。

安全性判断标准：**被重写的提交是否只属于自己的、还没推送给别人的本地提交**。
- 只有自己的本地提交 → force push（建议 `--force-with-lease`）安全
- 公共历史（别人可能基于旧哈希工作）→ 危险，别人基于旧哈希的工作会全部悬空。金科玉律：*Never rebase public history.*

**评分要点**：
- 指出 rebase 是重建哈希不同的新提交（parent 变了），而非移动（1 分）
- 解释 push 失败 = 非 fast-forward，因历史被改写（1 分）
- 给出安全边界：仅限未推送的私有提交，公共历史不可 rebase（1 分）
</details>

## Q4：merge vs rebase 的取舍

你在两台设备（台式机 + 笔记本）上维护同一个个人笔记仓库，经常两边都有未同步的提交。

(a) 为什么这里推荐 `git pull --rebase` 而不是普通 `git pull`？请描述 `--rebase` 的三步过程。
(b) 如果工作区还有未提交的改动，`pull --rebase` 会被阻塞，怎么办？
(c) 为什么说这个场景下 rebase 的"改写历史"缺点不成立？

<details><summary>参考答案</summary>

**(a)** 普通 `git pull` 默认走 merge：远端有本地没有的提交时会造出 merge commit，多端频繁同步会让历史变成反复分叉的"地铁图"。`pull --rebase` 保持直线历史，push 必然是 fast-forward。

三步过程：
1. 把本地**还没推送**的提交临时摘下
2. 快进到远端最新（等价于 fetch + 移动指针）
3. 把本地提交逐个**重放**到最新基点之上

**(b)** 使用 `git pull --rebase --autostash`：先自动 stash 未提交改动，rebase 完成后再 pop 回来，避免脏工作区阻塞。

**(c)** rebase 的危险在于改写**公共历史**（别人基于旧哈希的工作会悬空）。个人笔记仓库的提交只属于自己的、未推送给他人的本地提交，完全落在安全边界内，没有"别人"会受影响。

**评分要点**：
- (a) 说出 merge commit / 分叉历史问题 + 三步过程（摘下→快进→重放）（1 分）
- (b) 答出 `--autostash` 及其 stash/pop 机制（1 分）
- (c) 指出安全边界是"只属于自己、未推送的提交"，个人仓库满足（1 分）
</details>
